# senTRA — geospatial intelligence prototype with satellite and globe

**senTRA** means **Service & Epidemiology Network for Tracking, Routing & Access**. This student-led scientific and technological innovation represents the Department of Biochemistry, Faculty of Science, Adekunle Ajasin University (AAUA), Akungba-Akoko, Ondo State, Nigeria, for the **USPF Changemaker Challenge 2026 — Healthcare Sector**. Project representation does not imply formal university endorsement or an institutional partnership.

> **Demonstration only.** All senTRA referral records, healthcare figures, facility-example names and positions, ownership and service tags, indicators and alerts are synthetic. Separate OpenStreetMap healthcare points are **unverified map context**, not senTRA facility records. GEOACCESS combines fictional facility points with published boundaries, a subset of GRID3 settlement points and **modeled 2020 population estimates**. Its access outputs are simulations, not measurements of actual care access or forecasts. Do not use the prototype for clinical, emergency, planning or resource-allocation decisions. There is no operational patient service, verified facility registry, live health feed or validated predictive model. **Never enter real patient information.**

## Satellite and globe visual update

GEOACCESS, Operations and MAMA-GUARD’s shared GEOACCESS map now offer **Satellite / Map**, an interactive **Globe**, 2D/3D controls, and an imagery provenance panel. The default global demonstration uses EOX’s 2024 Sentinel-2 cloudless mosaic (~10 m/pixel). At street scale the app searches the OpenAerialMap STAC catalogue for individually licensed, detailed scenes that intersect the viewport, overlays eligible results, and displays their contributor, capture date, nominal resolution, licence and catalogue link. A bounding-box match does **not** guarantee coverage of every visible pixel. Where no eligible scene is found (or the catalogue is unavailable), the map explicitly falls back to mapped context instead of passing enlarged 10 m pixels off as detail; a control can show the coarse mosaic anyway. Images are historical, not live. 3D uses terrain and approximate OSM building blocks—not photorealistic building models.

**The built-in EOX and many OpenAerialMap scenes are non-commercial demonstration sources.** Comply with their individual terms and visible attributions; commercial use requires the appropriate permissions or a different licensed source. For broader detail, expand **Connect wider high-resolution imagery** and provide your own MapTiler browser key; the MapTiler feed replaces both demo imagery sources and its logo/attribution are displayed. An optional `VITE_MAPTILER_KEY` can instead be supplied at build time. Browser keys are exposed to users and the provider, so restrict them to authorised domains and check coverage, pricing and licence terms. No key is included. The MapTiler connection was tested with a mocked provider, not a real account. **Use local map only** pauses imagery as well as OSM/DEM requests, subject to browser storage limitations; third-party imagery is not cached by the service worker.

## Quick start

Requirements: Node.js 22 LTS or newer, npm and a WebGL 2-capable browser. No API credentials, backend or database are needed for the existing local demos. To show the synthetic account backend's configuration status, start it and the optional same-origin proxy as described in [backend/README.md](../backend/README.md); without them the account page safely reports the backend as unavailable.

```bash
cd sentra
npm ci
npm run dev                 # Vite development server
# or build and run the production version:
npm run build
npm run preview
```

Open the displayed URL, usually <http://localhost:5173>. On a memory-constrained machine, stop unused development servers and try `NODE_OPTIONS=--max-old-space-size=768 npm run build`. Heap needs vary; a 640 MB cap failed on one Stage 4 build. Development and preview accept arbitrary hostnames for sandbox previews; harden host allowlists, security headers and access controls before any non-demo deployment.

## Stage 2: GEOACCESS

Open **GEOACCESS** from the sidebar. Its central MapLibre map shares the Stage 1 Nigeria base geography and optional mapped context; the Stage 1 command map still has its separate deck.gl analytical overlay. The workspace has eight interactive tabs:

1. **Spatial Overview** — boundary, modeled-population and mapped-sample summaries, plus state/FCT or LGA comparison.
2. **Facility Explorer** — search and filter the fictional points by type, illustrative ownership and service tags, verification and search extent. Details explicitly show operational status as unknown. Selecting "verified only" returns no records.
3. **Population Intelligence** — WorldPop's 2020 modeled counts and density, summarized over the selected geography. Values are not current census counts.
4. **Healthcare Accessibility** — great-circle nearest and multiple-nearest fictional facilities for a selected GRID3 sample settlement; tabular results and CSV export.
5. **Catchment Analysis** — adjustable straight-line radius circles, distinct coverage and multi-circle overlaps, with population-weighted centroid proxies.
6. **Underserved Communities** — only **potential distance-based candidates in a simulation**, not a determination of actual deprivation or need.
7. **Spatial Analytics** — DBSCAN clustering of fictional points, a settlement-to-facility distance matrix, and approximately projected/clipped Voronoi partitions for a selected state/FCT or LGA. A synthetic point-density layer is also available.
8. **Scenario Simulation** — remove a fictional facility, place a new fictional PHC, apply a hypothetical increase to population weights, remove a fictional referral destination, or add another fictional facility. Baseline and modified geographic proxies are recalculated using current filters. A referral-network scenario impact is unavailable: although the optional map overlay reads validated synthetic REFLEX examples, it does not model rerouting or capacity.

Use the shared geography selector to select a state or FCT, then the LGA dropdown or map to drill down. Enable **Ward boundaries** to load and inspect optional 2026 operational ward polygons for that state/FCT. Clicking a ward displays its name, source LGA and provenance; it does **not** change the selected state/LGA or compute ward-level metrics. Toggle layers and adjust the illustrative radius in the left panel; click features for metadata and nearest examples on the right. Facility search can be limited to the selected geography or include fictional points across Nigeria; this choice and other facility filters affect spatial comparisons and the synthetic network overlay. The map has 2D/3D, zoom, rotation, pitch, coordinate, scale, reset and expanded-view controls. When online terrain is available, 3D uses the Mapzen DEM; mapped building heights are approximate and the ambiguous 5 m default remains flat. Population density is a separate raster rather than elevation. Points, ward boundaries, radii, Voronoi and referral overlays can remain visible in 3D. Published geography and population are not independently verified by this project.

### What is actually calculated

- **Ward layer:** published operational polygons are an inspection-only overlay, not inputs to population or access calculations. They may cross or disagree with the separately sourced 2022 state/LGA boundaries. See omissions and known source defects below.
- **Distance:** Haversine great-circle distance on a mean-radius sphere (6,371.0088 km). It is not a road route, road distance, travel time, validated clinical recommendation or evidence a service is operational. The default 25 km threshold is an arbitrary demonstration control, not a healthcare standard.
- **Radius / overlap:** geodesic circles are centered on matching fictional facilities. Each sampled settlement is counted at most once for "within one or more" and separately as overlapping when it lies within at least two circles. With no matching points, distances and gaps are **unavailable**, not zero or an assertion of no real services.
- **Population-weighted proxy:** each ~9 km group of valid WorldPop source pixels (further split at administrative boundaries) is represented by its population-weighted centroid. The modeled count for the entire group is classified by the centroid's distance to matching fictional facilities. This is a coarse geographic proxy, not person-level coverage; border effects, within-cell variation and changes since 2020 are ignored. Mean nearest distance is weighted by these same counts. Overlap uses groups with two or more points within the radius, without double-counting population.
- **Scenario demand:** a uniform percentage increase scales the selected area's 2020 population weights as a hypothetical input. It is not observed healthcare demand; geometric percentages and distances are unchanged. Facility-removal/addition scenarios affect only fictional point locations, not actual capacity, staffing or service availability.
- **Spatial analysis:** DBSCAN uses a great-circle neighbourhood and includes the point itself in `minPoints`. The Voronoi diagram uses a local longitude scaling at mean latitude and is clipped to the selected administrative polygon; it is a planar approximation, not a road-network or geodesic service area. The distance matrix is a transparent 5 × 5 view of the first alphabetically ordered matching records; filters control its candidate points.
- **Population summaries:** WorldPop counts in people/pixel are summed, not confused with density in people/km². Valid cell area is derived as count / density; aggregated density is sum(count) / sum(area). Source pixels are rasterized to 2022 polygons by cell centre; ADM2 parent state/FCT is assigned by representative-point spatial join with largest-overlap fallback. Parent/border mismatches are excluded from ADM2 assignment. The national source raster sum is approximately **216,798,661 modeled people**; **216,602,569** are assigned to an ADM1 boundary. Approximately **196,092** are outside the ADM1 assignment; ADM2 assigned totals are lower again, by approximately **83,072** relative to ADM1, owing to boundary and cell-centre differences. Rounded per-area totals need not add exactly.
- **Raster display:** the transparent image is georeferenced to the original WGS84 grid, with a 4×4 aggregation of ~1 km source cells (~4 km at the equator), nearest-neighbour display and discrete density classes. The display remains national when a local area is selected; the highlighted geometry and calculations reflect the filter.

A nearer fictional point, an overlapping radius, a high density, or an out-of-radius settlement says nothing by itself about real care, actual service availability, need, deprivation, quality, physical barriers or travel time. No model is clinically validated. Mapped OSM roads are visual context only: no routable road graph, routing engine, capacity, stocks, staff, emergency feed, predictions or operational digital twin is included.

## Stage 3: REFLEX

Open **REFLEX** in the sidebar. It shares the global state/FCT selector and the same 111 fictional GEOACCESS facilities and LGA index. A facility can be inspected in GEOACCESS from matching, network and tracking: the example is selected, highlighted and focused on the shared map. The **Return to REFLEX** link returns to the originating tab; an unsaved synthetic form and selection stay in this browser tab's memory while navigating but are discarded on reload. No patient record is passed to the map.

The workspace contains nine sections:

1. **Command Centre** — ten calculated synthetic indicators plus in-transit, received, follow-up-due and counter-referral-pending measures, six-month activity, status/service distributions, origin geography, receiving workload and heuristic review signals. Shared filters and drill-downs apply.
2. **Create Referral** — synthetic reference, fictional origin/destination, requested service and optional required capability tag, priority, administrative reason, predefined non-diagnostic context, simulated permission, notes and dates. Review, edit a draft or submit a *local simulation*. A downloadable minimal text summary omits notes; the QR contains only the synthetic referral ID and is **not a secure token**. No message is sent.
3. **Facility Matching** — rank and compare fictional receiving examples using a required service tag, optional additional required tag, tag breadth, same state/FCT, straight-line proximity and record completeness. A per-candidate exclusion list explains missing tags or origin identity. Priority is displayed but not scored; readiness, capacity and live availability are unknown. A human chooses a destination. The confidence label is **synthetic / not verified**, not a calibrated probability or assessment of clinical suitability.
4. **Referral Network** — interactive D3 directed graph, keyboard facility/connection inspection and a MapLibre geographic view using shared boundaries. Node sizes and edges show synthetic volume. Degree, unweighted directed betweenness, directed density, weak components and top-receiver share are calculated; high inbound volume and low-connectivity examples are review signals only. Geographic lines are not road routes.
5. **Referral Tracking** — searchable register, synthetic identity/summary, details and timestamped event history, with permitted transitions. A rejection requires a fictional administrative reason. Event role labels are simulated context, not authenticated people. All statuses describe local actions, not verified events or actual transport.
6. **Counter-Referral** — a linked administrative response recording simulated receipt and completion, a fictional service category, non-diagnostic outcome, follow-up plan, return, date and synthetic notes. Receipt/completion must agree with the local timeline. A separate local acknowledgement is recorded in the timeline; it does not authenticate or contact anyone. Clinical findings and treatment instructions are unavailable.
7. **Follow-up Monitoring** — overlapping queues for upcoming, overdue, pending acceptance/receipt, counter-referral, acknowledgement, missed-appointment flags, uncompleted and potentially inactive examples. Predefined fictional attempt outcomes are recorded locally; the missed flag uses the latest attempt and requires pending follow-up. Rules are editable (1–90 whole days; escalation at least inactivity). Inactivity is a review proxy, not evidence of patient loss. No reminders are sent.
8. **Referral Analytics** — completion, rejection/counter-referral/follow-up rates with denominators, submission-to-completion delay bins, mean completed time-in-stage, event milestones, reason and service mix, geography, receiving workload, inactivity and graph-based review signals. Creation-date coverage is displayed. Milestone bars count ever-reached events; their drill-down applies **current** status. Delay-bin, service, status, facility and geography drill-downs are interactive.
9. **Simulation Laboratory** — hypothetically remove a receiving candidate, add a site, increase demand, add a fictional service tag, penalise a bottleneck, or increase a destination's workload weight. It compares recomputed baseline and modified assignments, ranked examples, weighted distribution, mean straight-line distance and an unweighted directed graph. Scenarios never alter saved records and are not predictions.

### Rules, calculations and data integrity

- On first use, the application creates **222 deterministic fictional examples** with synthetic `RFX-DEMO-...` referral IDs and `SYN-PT-...` references, plus synthetic events and follow-up dates relative to first opening. None represents a real person, institution or referral. They are not imported from a facility registry. Seed counts and time-based indicators change as examples are edited and time passes.
- Shared filters apply state/FCT and LGA to the **origin**, facility and fictional facility type to **either endpoint**, service to the requested category, status to the current status, date range to the creation date and text search to IDs/references/facility names. Drafts are included in general counts but excluded from submitted network edges and follow-up queues.
- Allowed status paths are Draft → Submitted → Awaiting acceptance → Accepted → In transit → Received → Service completed → Counter-referral issued → Closed. From Awaiting acceptance, a referral can instead be Rejected and then closed or given a counter-referral; from Received a counter-referral can be issued without completion, and from Service completed it may be closed without a counter-referral. Invalid jumps and inconsistent counter-referral flags are rejected.
- Completion rate is **ever reached service completed / ever submitted** among filtered records. Mean processing time is the arithmetic mean of nonnegative submission-to-completion event differences. Rejection analytics count examples ever rejected; inactivity counts open paths without a status change for the configured number of days. Overdue uses a pending follow-up strictly before the browser's current local date; upcoming includes today through the configured window. “Without completion” can include rejected or closed examples. Categories overlap and are not real-world performance measures.
- The illustrative match index is: exact fictional service tag **45**, tag breadth **up to 15**, same state/FCT **10**, great-circle proximity **up to 20** falling to zero at 500 km, and five populated fields **up to 10**. An optional additional fictional tag is an eligibility filter, not extra points; priority/urgency is **not scored**. Hypothetical penalties may be applied. There is no validated threshold or real readiness/capacity measurement. Results use the GEOACCESS Haversine distance, not a road route or travel time.
- Directed graph betweenness uses unweighted Brandes shortest paths, normalised by `(n − 1)(n − 2)` for `n > 2`; directed density is unique edges / `n(n − 1)` and components ignore direction. Top-receiver share is the largest inbound volume divided by submitted network volume. Low connectivity is in-degree plus out-degree ≤ 1. Only facilities appearing in a submitted valid edge are network nodes; isolated catalog facilities are **not** shown. Referral volume controls visual weighting, not shortest paths.
- Simulation recomputes a baseline by assigning each submitted example to its highest-scoring compatible fictional candidate, **not** to the recorded destination. An unavailable facility is excluded only as a receiver; a bottleneck applies an arbitrary **25-point** penalty; demand scales all example weights and workload scales assignments to one destination. Weight increases do not create individual referrals or infer a capacity-induced reroute. A new site uses input coordinates checked against simplified 2022 state/FCT polygons and carries fictional service tags. The scenario graph is unweighted; mean distance is weighted by projected assignments. Results are heuristics, not evidence of care access, a forecast or an optimisation model.
- Saved examples and rules use browser `localStorage` under `sentra-reflex-synthetic-v1`; settings are separate. Data are unauthenticated and unencrypted, can be lost when browser storage is cleared, and are not a secure audit trail. Same-origin tabs receive storage updates but concurrent writes are **last-writer-wins**, with no conflict resolution. If storage is blocked, the interface reports memory-only changes; malformed saved data are not overwritten until the user explicitly chooses **Reset REFLEX examples**. The reset button discards local REFLEX edits and reseeds; it does not reset Stage 1 preferences.
- Notes are for fictional administrative content only. The form blocks email- and phone-like patterns as a limited precaution, **not** as a reliable personal-data detector. Never enter names, actual identifiers, contact information, clinical details or patient information.
- Simulated permission is required for new submissions, but is neither real consent nor a sharing control. Version-1 snapshots lacking the new permission, context, capability or role fields remain readable; absence is displayed as not recorded/default context and is not fabricated in stored history. Older drafts must be edited to select simulated permission before submission. A missing additional capability is displayed as not recorded; for backward-compatible matching/simulation it adds no extra eligibility filter, which does not establish that no capability was required.
- Rejection rate = ever rejected / ever submitted; counter-referral completion = counter recorded among ever completed / ever completed; follow-up completion = completed / (pending + completed), excluding not-required and drafts. Time-in-stage means average intervals between consecutive status events; open intervals and auxiliary events are excluded. A zero denominator is displayed as unavailable.
- The QR code encodes only the synthetic ID, not a link, credential or protected record. The text summary is locally downloaded and intentionally omits notes. The local summary is not a real referral or secure exchange.

**Ward boundary limitations:** GRID3 v4.0 covers all states/FCT, but Benue, Cross River, Ebonyi, Plateau and Taraba retain older v1.0 boundaries. The provider reports that Ikuru ward geometry in Andoni LGA, Rivers was removed in error and its name assigned to part of Ataba 2; small gaps may occur at those five state borders. Of 9,335 source records, 28 have no geometry and one simplified geometry has no polygon after validity repair; these 29 are excluded and listed in `public/data/geoaccess/wards/missing-geometries.json`. Fifty-nine other invalid simplified geometries were repaired for display. ArcGIS simplification uses a 0.001-degree tolerance and four-decimal coordinate precision. No missing geometry is fabricated. The 2026 ward layer can differ from or cross the independently joined **2022** LGA boundaries; source LGA names are displayed as attributes only, not treated as analytical joins. Ward selection does not filter or recompute any analysis. Do not infer ward-level population, coverage, administration, legal boundaries, completeness or real access.

## Offline use and architecture

MapLibre GL JS is pinned to **6.18.0**. Its self-contained ES-module worker is served untransformed by the Vite development server, emitted as a hashed static asset for production, and registered via `setWorkerUrl` before any map is created. Revalidate worker packaging, WebGL 2 support, maps, offline caching and the dependency audit when upgrading MapLibre. `npm ci` warns that Recharts 2.x is no longer an active branch; plan a supported-version upgrade and chart regressions separately. A production service worker precaches the application shell, emitted JS/CSS/font assets (including the MapLibre worker) and the original local Stage 1 geography. GEOACCESS's public static derivatives, including the facilities and LGA index used by REFLEX, are **cached on demand**, not all precached: visit the desired state/FCT, settlement layer, ward layer and analytical tab once online before expecting those particular files offline. Open REFLEX online once to cache its facility and LGA index files. Previously unvisited region/analysis files return an explicit unavailable state offline; there is no invented fallback. A build-versioned worker uses the derived-asset manifest to invalidate old data. Service workers require a secure context (HTTPS or localhost) and browser storage; development mode does not register one. The worker does not cache API responses, patient data, OpenFreeMap tiles, DEM tiles, remote font glyphs, EOX imagery, OpenAerialMap catalogues/imagery or MapTiler resources; do not assume third-party geography will be available offline. On first visit, successfully loaded local JSON is requested again after worker control so it can be cached. Browser/provider HTTP caches are separate and outside this guarantee.

### Reproduce derived assets

The bundled derivatives are ready to use; regeneration is optional and needs Python, internet access and about 22 MB plus temporary source files:

```bash
python -m pip install -r scripts/requirements-geo.txt
python scripts/prepare-geoaccess.py
npm run test:geo
```

The script downloads the pinned geoBoundaries ADM2 release and the two specified WorldPop rasters, queries GRID3's settlement service in FID order and the operational ward service by state with OBJECTID-ordered pagination, joins geometry, generates population cells and raster, and writes a source manifest with SHA-256 hashes. Ward queries use 0.001-degree provider-side simplification and four-decimal coordinates; invalid display polygons are repaired and unusable geometries recorded, not manufactured. `public/data/geoaccess/wards/source-hashes.json` records checksums of normalized state-level query responses. `/tmp/sentra-stage2` is used as a download cache, including `/tmp/sentra-stage2/wards-v4/`. Live sources can change over time; exact reproduction requires preserving source snapshots and recorded checksums. To regenerate Stage 1's synthetic points separately, run `python scripts/prepare-geography.py` with Shapely installed; this changes the synthetic seed-derived files and requires Natural Earth access.

## Safety and future work

The new identity API enforces sessions, resource-level checks, scoped synthetic consent and local audit only for its fixed synthetic examples. No real provider, real consent management, independently protected audit, encryption workflow, FHIR endpoint or production database is connected. Simulated module roles, permissions and local acknowledgement are not security or consent. A future deployment requires authorised sources, reliable and current facility coordinates, verified operational availability, road-network data, a protected durable database, privacy/security design, concurrency control, uncertainty analysis, clinical/public-health governance and independent validation. Neither the geospatial nor maternal demonstrations make the platform operational.
