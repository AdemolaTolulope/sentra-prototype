# Stage 4.5 — geospatial rendering audit and implementation plan

Audit date: 12 November 2026 (Africa/Lagos). This is a historical pre-implementation assessment; proposed features below are not claims of completion. The existing Stage 4 application and previews were the baseline. See the [implementation note](STAGE4.5-IMPLEMENTATION-NOTE.md) and [Stage 4.5 handover](../HANDOVER-STAGE4.5.md) for the implemented outcome.

## 1. Current architecture and causes of the flat experience

- `src/components/map/mapBase.ts` defines a **local, simplified administrative style**: Natural Earth neighbours, GRID3/geoBoundaries state polygons and fictional Stage 1 markers. It has no street, waterway, building, elevation or city-label source.
- `src/geoaccess/components/GeoMap.tsx` is already reused by GEOACCESS, Operations and MAMA-GUARD. MapLibre renders local layers; deck.gl adds administrative population-density extrusions in 3D. These are not terrain. The Operations view exaggerates that density height substantially. The extrusions can obscure local geography, and most 2D points, ward, catchment and gap layers are hidden in 3D.
- Camera limits prevent the requested detail: GEOACCESS tops out at zoom 13; the Stage 1 command map at 11; REFLEX's geographic network at 12. An imported facility is centered at zoom 8.5. State and LGA `fitBounds` do not provide an actual community/facility exploration path.
- The command-centre `IntelligenceMap` and REFLEX `NetworkMap` each instantiate MapLibre separately. They share the same local base-style function but not the complete GEOACCESS map component. The upgrade should share one **geographic context/terrain layer installer** across all three map types rather than introducing another rendering engine or inconsistent datasets.
- Published local context currently includes 37 ADM1 areas, 774 simplified LGAs, 9,306 renderable GRID3 ward polygons, a 2,924-point non-representative GRID3 settlement sample and WorldPop modeled 2020 population. These sources have differing dates and limitations. There are **111 fictional facilities**, including 19 with a fictional maternal-care tag; all operational availability is unknown. REFLEX referrals and MAMA-GUARD profiles are synthetic.
- No road network, building footprints, DEM, current facility registry, road routing, live incident feed or operational readiness dataset is bundled. A mapped road will not establish passability; an OSM building will not establish a healthcare facility; modeled population is not demand.
- The production service worker precaches the local shell and caches visited same-origin public GEOACCESS data. It does not cache third-party maps or protected records. The existing local geography can therefore serve as the offline/failure fallback.

## 2. Source and technical feasibility checks

1. **OpenStreetMap / OpenMapTiles through OpenFreeMap**: the public [service](https://openfreemap.org/) documents a MapLibre vector endpoint, no API key, OSM attribution and no SLA. The tile schema supplies roads, water, settlements/place labels, aeroways and building footprints. On the audit date the browser successfully fetched its TileJSON with CORS; the current TileJSON referenced a 1 November 2026 snapshot, but it is a rolling service, not a guaranteed vintage. Coverage and currentness vary. [OpenStreetMap copyright/ODbL](https://www.openstreetmap.org/copyright), [OpenMapTiles attribution](https://openmaptiles.org/) and [OpenFreeMap terms](https://openfreemap.org/tos/) must remain visible. Do not bulk-prefetch or imply the service supports routing.
2. **Mapzen/Terrain Tiles, AWS Open Data**: the [AWS registry](https://registry.opendata.aws/terrain-tiles/) describes a global, bare-earth DEM. Browser GET and CORS were tested for a representative Nigerian Terrarium tile; its metadata cites SRTM/GMTED. Terrain varies by source and is not necessarily current. Credit Mapzen/Terrain Tiles, USGS SRTM/GMTED2010 and relevant [source attribution](https://github.com/tilezen/joerd/blob/master/docs/attribution.md); no API key is required for the tested endpoint. Successful access to one tile is not a reliability guarantee.
3. **Buildings**: [OpenMapTiles](https://openmaptiles.org/schema/#building) describes `render_height` as approximate; its [Planetiler implementation](https://github.com/openmaptiles/planetiler-openmaptiles/blob/main/src/main/java/org/openmaptiles/layers/Building.java) assigns a **5 m default when no height or level exists**. The renderer must not portray that default as a verified real building height. Plan: show mapped footprints flat, and only extrude suitable non-default source heights as approximate/unverified. This conservative filter also omits genuine heights indistinguishable from the default. One-tile probes in Lagos, Abuja and Ikare found different amounts of road/building detail; they are feasibility checks, not coverage statistics.
4. **NHFR**: no authorised current API, credentials, data-sharing agreement or operational availability feed has been provided. Retain fictional facility IDs and clearly mark verification/availability. Do not turn OSM POIs into verified facilities or infer readiness.
5. Network dependencies are optional. Remote tile requests disclose the viewer's IP address and geographic viewport to the provider; the app must disclose this and must not send referral or patient records. OSM/DEM data will not be bulk-downloaded or represented as guaranteed offline.

## 3. Planned milestones

1. **Audit (this document):** preserve the current modules and make sources and limitations explicit.
2. **Shared geographic foundation:** keep MapLibre/deck.gl; install one shared optional OSM-vector context and true DEM terrain/hillshade above the local base. Render water, differentiated roads, settlement/city labels and mapped building footprints. Add only conservative, source-supported approximate building heights; retain a clearly identified local fallback if any optional source fails. Keep legacy density extrusion available only as an explicitly labelled analytical overlay rather than confusing it with terrain.
3. **Progressive zoom:** raise the camera zoom limit; provide smooth state, LGA, sample-settlement and synthetic-facility navigation, appropriate zoom levels and scale indicators. Avoid changing the identity or position of a synthetic facility. Declutter labels and use real tile zoom levels rather than generated neighbourhoods.
4. **Healthcare overlays:** keep boundaries, modeled population, synthetic facilities, settlements, distance radii and gap candidates independently controllable and usable at relevant scales. Add a synthetic REFLEX network overlay and fictional maternal/emergency-tag layers where the existing data supports them. Mark live public-health, real emergency coordination and real coverage as unavailable instead of inventing them.
5. **Facility exploration:** extend the existing context panel with provenance, unknown operational status, nearby *sampled* settlements/facilities and available map-visible road names; retain original facility IDs and REFLEX/MAMA-GUARD handoffs. Clearly label straight-line distances and incomplete source coverage.
6. **Visual refinement:** fit the existing dark emerald/gold palette with differentiated blue water, road hierarchy and readable labels. Add compact context/terrain controls, provider status and attribution. Show a separate live development preview after the foundation and update it as work progresses; retain the current Stage 4 preview until the upgrade has been tested.
7. **Regression and handover:** exercise real online map loading and navigation, layer combinations, source errors, offline local fallback, keyboard/mobile layouts, facility identities and existing GEOACCESS/REFLEX/MAMA-GUARD/Operations/command workflows. Record only actually executed checks and capture national, state, LGA, community and facility views.

## 4. Safety and constraints

No new backend, credentials or new rendering engine is planned. Browser-side provider requests carry only map tile/viewport context, but these are still potentially sensitive; real patient data remain prohibited. No feature can establish a facility is open, equipped, staffed or accepting patients; no road is a route or travel-time estimate. Public-health and emergency-service feeds remain unconnected. Clinical, security, privacy and accessibility certification are not implied.

## Implementation refinement: mapped healthcare context

During implementation, a small number of ordinary on-demand OpenMapTiles probes confirmed that its `poi` layer contains mapped healthcare categories in some locations. Stage 4.5 can therefore show these as **unverified OSM map context**, independently of the 111 fictional senTRA facilities. Such POIs are not official registry matches: tile feature IDs are not asserted to be stable source IDs, the observation date is not supplied, and a mapped point does not prove current operation, service capability or readiness. They are excluded from REFLEX, MAMA-GUARD and all accessibility/scenario calculations; no cross-module handoff is offered for an unmatched OSM point. Existing synthetic facility IDs and their handoffs remain unchanged. The POI layer can be disabled, as can all online geography.
